# Journal — 2026-08-09 — Post-1.0 economy analysis and mode fork

Decision record for the first post-release planning session. Deliberately
holds what the specs omit: rejected options and the reasoning that would
otherwise have to be re-derived.

## The finding that reordered everything

The loss condition reads `inventory.length < getAnswerLength(equation)` —
"you run out of tiles". That is not what kills a run.

Reward tiles are drawn uniformly from `0–9`, so a hand drifts toward uniform
composition. With `P(both digits present) = 1 − 2(0.9)ⁿ + (0.8)ⁿ` weighted
across the 45 pairs (13 one-digit products, 32 two-digit), the **buildable
rate** at capacity 10 is `b ≈ 48%`. Roughly half of all equations cannot be
spelled from the hand *regardless of arithmetic skill*.

Combined with net `+1` per correct answer against `−1.71` average per forced
miss, drift is `b·1 − (1−b)·1.71`, crossing zero at **`b ≈ 63%`**. Because
`INVENTORY_CAPACITY` is a reflecting ceiling, that threshold is a **cliff**,
not a slope: below it runs die in ~22 rounds; above it they never end.

Every item on the feature wishlist raises `b`. The 1.0 balance is therefore
**near an unchosen cliff edge, which is not the same as balanced.**

All figures re-derived programmatically during spec review, not carried from
mental arithmetic.

## Rejected: three counterweight drains

The cliff exists because reward is `N+1` against a fixed ceiling. Four
candidates were modelled for making run length a function of skill rather
than luck. **Shrinking capacity won** (it becomes Classic mode). The other
three, recorded so they are not re-proposed:

- **Decaying reward** (`N+1` → `N` after round X). *Mathematically the best
  answer* — net-per-correct becomes 0, so lifetime is `C / ((1−b)·1.71)`,
  smooth in `b` with no threshold anywhere. **Rejected because** at reward
  `N` you never exceed capacity, so you never discard again. The game's
  signature decision switches off exactly when the run should be tightest.
- **Streak-gated reward** (`N+1` only after a correct answer). Only moves the
  cliff from `b = 0.63` to `b = 0.71` and leaves it a cliff. Buys one
  feature's headroom, fixes nothing structural.
- **Flat tile decay** (lose a tile every K rounds). Structurally identical to
  streak-gating — shifts the cliff without removing it — and drains the
  player without ever changing a decision.

Insight worth keeping: **a cliff at an unknown, luck-determined position is
unfair; a cliff at a scheduled position is a climax.** Shrinking capacity
does not remove the cliff, it reschedules it. That reframing is why it won.

## Cut features and why

- **억까 (deliberately hostile random).** The game has no channel to signal
  intent, so hostile generation is observationally identical to variance. It
  produces resentment, not difficulty.
- **유물 (relics).** A meta-system needing run milestones to attach to. A
  separate project, not a feature.
- **Constructibility warning / Pass action.** Ori's call, and correct on
  better grounds than first stated: the deliberate-wrong-answer exit lets the
  player choose *which* tiles to jettison, making it strategically richer
  than a Pass button. It is a manual discard that is already correctly
  priced, not a hack to be removed.

## Numbers worth not re-deriving

- **Capacity 13 is the ceiling** if the economy is otherwise unchanged.
  `b(13) = 60%`, `b(14) = 64%` — 14 already tips past the cliff. Useful the
  next time a capacity bump is proposed.
- **Kind-equation bias caps at ~20%** in Endless. `b' = p + (1−p)·0.48`
  gives 58% at p=0.2 and 63.6% at p=0.3.
- **No product of two operands in `1–9` has a repeated digit** (verified by
  enumeration). This is load-bearing: it means a perfect one-of-each starting
  hand builds 100% of equations, so a run is precisely the story of that hand
  degrading.
- The `b ≈ 48%` baseline assumes a *uniform* hand. A player discarding to
  maximise coverage does better, so real `b` is somewhat higher and the
  margin to the cliff is thinner than the model implies.

## Codebase findings

- **The `+1` duplication footgun.** `App.tsx:48` generates the reward count
  and `gameReducer.ts:62` validates it, both as the literal expression
  `selectedTiles.length + 1`. Changing one without the other makes the
  reducer guard reject the action and return unchanged state — every correct
  answer silently stops working, with no error. This is why
  `getRewardCount()` is being introduced; recorded here because the refactor
  removes the evidence.
- **Overflow phase has no keyboard path.** `useGameKeyboard.ts:53-60`
  handles only `Enter`, so a keyboard-only player cannot choose *which* tile
  to discard without a mouse. Being fixed in the Endless build.
- **Motion is the least tokenized layer** despite 25 tokens and zero
  hardcoded colors: `150ms`/`100ms`/`translateY(1px)` repeat across 7 CSS
  modules.

## Decisions (Ori)

- Fork into two modes: **Endless** (survival, fixed capacity, rounds
  survived) and **Classic** (shrinking capacity, streaks). Endless ships
  first; Classic is the following build.
- Mode name "Classic" kept for the shrinking mode after the concern was
  raised that players read "Classic" as meaning the original.
- Kind random **in at 20%**; capacity 20, wildcards, and special tiles all
  relocate to Classic rather than being dropped.
- Design system scope: token/motion discipline plus a dev-only states
  gallery. Live tuning panel and Figma sync rejected as disproportionate.
- Tuning surface folds into the Endless build; gallery gets its own.

## M4 close-out — what the final review actually caught

The four gates (lint, typecheck, test, build) passed at every task boundary
and still missed a whole class of defect. Mutation testing found all of it.
Worth repeating on later milestones:

- **A dial passed as a parameter is not a tuning surface.** Replacing
  `KIND_EQUATION_RATE` with a literal `0.5` at App.tsx's three call sites
  left all 201 tests green and made the game unloseable — `balance.test.ts`
  would have kept guarding a value the game no longer used. Fixed by
  deleting the parameter: `generateKindEquation` imports the dial, as
  `getRewardCount` imports `REWARD_BONUS`. **Rule: injection is for
  impurity (`RandomSource`, `TileIdFactory`), never for constants.**
- **Guard tests must bracket a constant tightly.** A loose bracket (gate
  0/0.99) passes against *any* threshold; only `RATE ± 0.001` catches a
  rewired one. Such a test is self-referential by design — it pins the
  wiring, not the value, so `tune(balance):` commits never break it.
- **CSS Modules fail silently, twice over.** `styles.actions` with no
  matching class renders `class="undefined"`; `.primary` (0,1,0) loses to
  `.entry dd` (0,1,1) and the emphasis is simply dead. Neither is caught by
  any gate. The specificity loss survived a full task review.
- **`disabled={false}` passed everything.** A prop with no assertion is an
  unimplemented feature that looks implemented.

Doc drift is the same class of silent failure. The capacity comment carried
numbers from the model as it stood *before* the kind bias existed, so it
advised a safe range (up to 13) that now fails the invariant at 11. Numbers
in comments need a recomputation pass whenever the model behind them moves.

## Verifying reduced motion without a perceptible signal

T19 step 5 asked for a browser press-test with OS reduce-motion enabled. The
check was unfalsifiable as written: the app's entire motion surface is a
150ms border-color fade and a 100ms 1px `translateY`, so "press a button and
confirm no transform offset" produces the same nothing whether the override
fires or not. Ori ran it and correctly reported seeing no difference.

What settles it is forcing the gate open from the CSSOM and reading computed
style, with the OS setting out of the loop entirely:

```js
rule.media.mediaText = 'all';                       // the @media (prefers-reduced-motion: reduce) rule
getComputedStyle(button).transitionDuration;        // '0.15s, 0.1s' → '1e-05s'
rule.media.mediaText = '(prefers-reduced-motion: reduce)';  // restores
```

The `!important` block wins over module rules of higher specificity, which is
the same mechanism `*:active { transform: none }` relies on — importance
sorts before specificity. All seven `translateY(var(--press-offset))` sites
were confirmed to sit under an `:active` selector; one applied via a plain
class would slip past that override.

**Generalizable:** when an acceptance criterion is "look at it and confirm
nothing happens", it cannot fail. Reach for the computed value instead.
