# Journal — 2026-08-12 — M5 gate zero and preflight

## Gate zero: Vite does not auto-discover sibling root HTML entries

Both GitHub issue #32 and `docs/plan/tuning-and-design-system.md` §5 assert
that a root `gallery.html` needs no `vite.config.ts` change, because Vite's
default build input is the root `index.html` alone. `vite.config.ts` sets no
`rollupOptions.input`, but that is only half the claim — whether Vite 8.1.5
*also* auto-discovers sibling root HTML files was never verified. If it did,
M5's exit gate ("`npm run build` emits no `dist/gallery.html`") would fail on
arrival.

Probed with a stub file before writing any task against the premise:

```
printf '<!doctype html><title>probe</title>' > gallery.html
npm run build && ls dist/
```

**Result: not emitted.** `dist/` contained `assets/`, `favicon.svg`,
`index.html` and nothing else. The premise holds; no config change is needed.

The complementary half — that the dev server *does* serve `/gallery.html` —
was verified separately, and the check has a trap worth recording. A plain
status-code check proves nothing: `curl` against `/nonexistent.html` also
returns **200**, because the dev server SPA-falls-back to `index.html`. The
proof is the response *body*. `/gallery.html` returned `<title>probe</title>`
plus the react-refresh preamble, meaning Vite transformed the real file.

The same trap applies to `npm run preview`, which is why the M5 plan treats
production 404 plus `ls dist/` as the exit gate and preview as advisory only.

## Deferred: `package-lock.json` is out of sync with `package.json`

`npm install` in a fresh worktree dirties the tree by 3 lines — it writes the
`engines: { node: ">=24" }` block into the lockfile's root package entry,
where it is currently absent. Reverted rather than carried, being unrelated to
M5. Worth folding into the next chore commit that touches dependencies, so a
fresh clone does not report a dirty tree after its first install.

## The anti-drift claim was false when it was written

`docs/plan/tuning-and-design-system.md` §5 justified the gallery partly on
this: states "compose from the existing `src/test/fixtures.ts` helpers, so
gallery states cannot drift from the states the tests assert against."

`fixtures.ts` exported only `makeAnsweringState`. `makeFeedbackState` and
`makeOverflowState` were defined twice, in two test files, and the two copies
had **already drifted** — one zeroed the feedback inventory, the other kept a
full hand; one hardcoded `correctValue: 9`, the other used `equation.product`.
A gallery built on either copy would have shown a state half the suite does
not assert against.

T21 existed to make the claim true before anything depended on it. The
reconciliation was chosen by probe rather than by argument: both differences
were unified locally and the suite run, which passed 204/204. That is what
licensed the "zero test-body edits" gate — it was measured before it was
promised, not asserted and hoped for.

The general lesson, and this is now the second time in two sessions: **a plan
that cites a property of the codebase should verify the property before the
tasks that depend on it are written.** Gate zero caught one such assumption;
this caught another. Neither cost more than a few minutes to check.

## Two review findings worth keeping

**A brief can specify a vacuous test.** T22's brief proposed
`getByText("7")` to prove the terminal equation renders. It would have
passed whether or not the equation was there — `7` is also the score. The
implementer caught it, proved the vacuity by removing `EquationBoard`, and
landed `getByText("7 × 8 =")` instead. `EquationBoard` renders four sibling
text nodes under one `<p>`, and Testing Library concatenates only an
element's direct text children, so that string is unique to the equation.

**Manual-check claims need artifacts.** Two implementers narrated browser
passes; neither kept anything inspectable, and the second could not drive a
browser at all. Narrative is not evidence. The pass was done by hand instead —
which the gallery made cheap, and which is the entire point of having built
it.

## The gallery found three bugs the suite could not

Its first act was to justify itself. Nothing below failed a test, a
typecheck, or a lint — all three were visible only by looking, which is the
argument for the gallery stated as a fact rather than a hope.

1. **The answering entries did not conserve tiles.** They built a selection
   by *adding* `selectedTiles` on top of a full inventory, rendering 11 and
   12 live tiles where `SELECT_TILE` *moves* a tile and the game shows 10.
   Tile count drives tray wrapping at 320px, so this was a layout the game
   never produces. Fixed by building the states through the real reducer —
   conservation now holds by construction rather than by assertion.
2. **The overflow entries showed an "Incorrect" panel.** They inherited
   `makeFeedbackState`'s default `lastResult`, but only `SUBMIT_CORRECT`
   grows the inventory past capacity, so overflow always follows a *correct*
   answer.
3. **Fixing (2) split the reward badges.** Naming `rewardTileIds` lit up the
   feedback panel while the same tiles sat unbadged in the tray, because the
   fixture builds every tile `isNew: false` and `TileInventory` draws its
   badge from `isNew`. A fix introducing a smaller instance of the defect it
   fixes is worth expecting, not just worth catching.

**A scope criterion is a criterion, not a verdict.** The unsorted overflow
inventory (#49) was ruled out of M5 because tile count — and therefore
layout — was identical. Stamping badges made tile *position* visible, and the
same criterion then ruled it in. The rule did not change; the change moved
across it.

**`sortTiles` breaks digit ties on string ids.** `"tile-11" < "tile-2"`, so
the twelfth tile files ahead of the third. Predicted wrong by hand, corrected
by the implementer running the actual code. Hand-tracing a comparator is
guessing.

## Measuring beat screenshotting

The visual pass at 320px was blocked twice — the Chrome extension reported a
successful resize while the viewport stayed at 1920 and clicks never landed,
and Playwright's profile was locked by an orphaned browser from earlier the
same day (killing it cleared the lock).

What finally ran was better than what was planned. Instead of eyeballing
screenshots, each state was measured in-page: `documentElement.scrollWidth`
against `clientWidth` plus a sweep for any element whose right edge exceeds
the viewport, then `main.innerText` and the tray's accessible names. That
yields quotable evidence rather than a claim about a picture — `0 0 1 1 2 3 4
5 6 7 8` with badges on the second `0` and second `1`, 9 tray tiles beside
one filled slot, `scrollWidth` 305 against a 305 viewport, 0 offending
elements. Worth reaching for first next time, not third.
