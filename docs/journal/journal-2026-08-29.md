# Journal — 2026-08-29 — M5.5 scoping and the M5 close-out

Decision record for the session that inserted `M5.5 — Design Pass` between M5
and M6 (#53, `d2da2a5`) and closed M5 out. M5.5 has not started; this holds
why it exists and what its contract actually permits, which is the part most

## The plan measured consistency; the heading claimed aesthetics

`docs/plan/tuning-and-design-system.md` §2.1 was headed "Visual layer —
already 80% there", and §3 defines "design system" for this project as
token/motion discipline plus a dev-only states gallery. Every one of those is
a *consistency* mechanism. The 80% is real and it was measured — 25 tokens,
zero hardcoded colours across 11 modules. It is a claim about internal
consistency, and no section anywhere asks whether the UI looks good.

The number was never the problem; the heading was. "Visual layer — already
80% there" reads as *the visual layer is nearly done*, which is not what was
measured, and with M5.5 now existing that reading is actively misleading.
Scoped to "consistency already 80% there", with a note stating what the
section does not measure, and the same pointer added in §3, §5, and §6.

The §3 decisions table was **annotated, not rewritten**. Those decisions were
correct for the question they answered. **A record that answered a narrower
question than its heading implies needs its scope stated, not its answers
revised.**

## A fraction beats renumbering when the alternative falsifies a journal

The design pass was not on the roadmap when M6 and M7 were numbered, and it
has to run after the gallery exists — the gallery is what makes every state
viewable without playing to it, which is the precondition for tuning them.

Rejected: renumbering M6 and M7 down. That would touch

## "Cannot introduce a hue" was false, and the disproof was in the file it cited

As first drafted, roadmap §4.1 argued that a pass confined to §1.12 "can fix
hierarchy, type scale, spacing, and density but cannot introduce a hue, a
dark mode, or a motion-based closure moment."

The first clause is wrong. §1.12 reads "High-contrast typography, neutral
surfaces, restrained accent use." It constrains **surfaces** to neutral and
asks only that accent use be *restrained*; it nowhere requires an achromatic
palette. `src/styles/global.css` — the file the argument cited as proof the
implementation is faithful — already ships five hues under that same
contract:

```
--color-correct:    #15803d
--color-incorrect:  #b91c1c
--color-reward:     #92400e
--color-discard:    #9a3412
--color-focus-ring: #2563eb
```

`--color-accent: #27272a` is therefore the implementation's *choice*, not the
contract's demand. Retuning it to a restrained chromatic value is phase 1
work and needs no amendment.

Caught by the automated reviewer on #53, not by anyone who read the paragraph
while writing it. **A claim about what a contract forbids should be checked
against what the codebase already does under that contract.** The disproof
was five lines in the file the claim named as its own evidence.

The shape of the fix is worth keeping too. The reviewer offered two options —
delete "a hue", or identify the narrower change that actually conflicts. The
second is right: deleting leaves weaker prose and still carries the
inaccuracy, whereas the real conflict is **surfaces**, a genuine §1.12
constraint. What replaced the list:

- **chromatic surface tint** — "neutral surfaces" forbids it outright
- **motion-based closure moment** — "no decorative motion" forbids it outright
- **dark mode** — the spec does not mention `color-scheme` anywhere, so this
  adds a rule rather than relaxes one

## The correction had to reach three artifacts, not one

Fixing `roadmap.md` left the claim standing in two other places:

- the #53 PR description — "a pass confined to §1.12 cannot reach the
  palette"
- tracking issue #52, where the copy had degraded further into "There is no
  hue anywhere in the game except the focus ring" — flatly false, and
  contradicted by "four semantic state colours" in its own preceding clause

#52 is the brief a future implementer opens first. Left alone, the
misdirection removed from the roadmap would have been the version that
actually got read. **A doc claim worth writing down was probably worth
restating somewhere else too; grep the GitHub artifacts, not just the tree.**
`docs/plan/tuning-and-design-system.md` was checked the same way and was
clean.

## Correcting a reason is not the same as moving a decision

Of the three items, dark mode's *reason* was wrong but its *phase* was right.
The spec is silent on `color-scheme`, so "§1.12 prohibits it" is false —
while "needs a spec edit, therefore phase 2" still holds, because adding dark
mode adds a rule where none exists. Rewriting it as silence-not-prohibition
leaves phase membership unchanged.

Landing it in phase 1 as permitted-by-silence would have changed what M5.5
contains. That is Ori's call, not a review-response call. **When a correction
could also expand scope, correct the stated reason and leave the scope where
it was.**

## A default-filtered listing is not the population

M4 and M5 both sat at `open=0` with every issue closed, yet stayed open as
milestones. `gh api repos/.../milestones` returned only those two plus M6,
M7, and M5.5, which supported an inference that this repo leaves milestones
open on ship and records closure in `roadmap.md` prose instead ("M0–M3 are
closed").

The inference was wrong. The endpoint defaults to `state=open`. With
`?state=all`, M0–M3 are all present and all closed. There was no convention;
M4 and M5 were simply untidied. Both are now closed, and closing M5.5's
milestone when it ships is the convention.

**Same class as the `curl` 200 trap in `journal-2026-08-12.md`: a check
whose default behavior manufactures the answer you expected.** There the SPA
fallback returned 200 for a file that did not exist; here the default filter
returned a milestone list that looked complete. When absence is the evidence
for a conclusion, check what the query excluded before believing it.
