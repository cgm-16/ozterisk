# Journal — 2026-08-30 — M5.5a, and what the design handover got wrong

Decision record for the session that amended the visual, copy and motion
contracts to permit `docs/design-system/`, and split `M5.5` into seven
merge-sized milestones. No `src/` was touched. This holds the measurements —
they are the expensive part to re-derive, and three of them contradict the
design system's own documentation.

## The amendment moved to the front because the design already existed

`journal-2026-08-29.md` scoped M5.5 as two phases: phase 1 working inside §1.12,
phase 2 proposing an amendment argued from gallery screens. That framing was
right for its moment and assumed the design work had not been done yet.

It had. `docs/design-system/` is a complete system, and it contradicts §1.12,
§1.14, §1.15, `product.md` §1.10 and the AGENTS.md motion constraint — four
gates where the roadmap anticipated one. Arguing an amendment from screens you
produce by violating the contract inverts document precedence. So the amendment
became the first step, argued from the design record instead, and every code
milestone after it is compliant by construction. A rejected amendment now costs
no merged code, which the phase-2 ordering could not promise.

The earlier reasoning was not rewritten. It was correct about a different
situation.

## Three claims in the handover were wrong, and each was silent

None of these would have failed a gate. That is what makes them worth recording.

**The focus ring fails WCAG on the app's most common control.**
`--focus-ring: --gold-300 #e8cd85` measures `1.10:1` against the ceramic tile face
`#e6d7ba` and `1.51:1` against the gold language segment. SC 1.4.11 needs `3:1`.
It passes comfortably on felt (`8.7:1`) and on the vermilion primary button
(`3.55:1`) — which is exactly why it survives casual review: the ring looks fine
everywhere except on the one element there are ten of. §8.5's "Visible focus on
every control" cannot catch a ring that is visible on four surfaces out of five,
so the checklist item now names the ratio and the surface.

**Zen Kaku Gothic New does not set Korean.** `readme.md` said it was chosen
"partly because it sets both scripts" and `guidelines/type-ui.html` said "one face
for both locales, Korean is not a fallback". It is a Japanese family; Google Fonts
serves it no Hangul subset, and neither EB Garamond nor IBM Plex Mono covers
Hangul either. Every Korean string would have fallen back to `system-ui`.

§8.5 has a "Korean copy does not clip" box, and it would have passed — `system-ui`
renders Hangul perfectly well. The failure mode of a missing font here is not
tofu, it is *the design silently not applying to half the users*. A checklist item
about clipping cannot detect that; §1.12 now requires each locale to render in a
face covering its script.

**There is no responsive layer at all.** The token set carries zero breakpoints;
the only media query anywhere in it is `prefers-reduced-motion`. A `5 × 2` rack of
`64px` tiles with `12px` gaps is `368px` before padding, against §8.5's `320px`
no-horizontal-scroll gate. The mobile rack *was* designed — the redesign document
picks option `3a`, `66 × 64` tiles solved for `390px` — but it was never
tokenised, and `390px` is not `320px`. §1.12 now fixes three tiers.

The pattern across all three: **a design system derived from a codebase inherits
the codebase's blind spots and states them as decisions.** The repo had no
responsive tokens, so the system has none. Checking a handover against the gates
is not the same as checking it against the code it came from.

## The rack redesign needs no reducer change

The design requires that selecting a tile not reflow the rack — the tile keeps its
socket, marked as on loan. The shipped `SELECT_TILE` removes it from `inventory`,
which compacts the rack.

But `SELECT_TILE`, `RETURN_TILE` and `CLEAR_SELECTION` all preserve the union
`inventory ∪ selectedTiles`, and `sortTiles` orders by `(digit, id)` — a total
order. So the rack is derivable presentationally in `GameScreen`:

```tsx
tiles={sortTiles([...state.inventory, ...state.selectedTiles])}
liftedIds={state.selectedTiles.map((t) => t.id)}
```

`src/game/` is untouched and `gameReducer.test.ts` — 892 lines — never runs.
Worth stating as a prohibition rather than a convenience: the handover's own UI
kit shipped a real bug in this area, gating game over on `canConstruct` instead of
`canAttemptEquation` and ending runs with ten tiles on the rack. It is a state
tour, not a reducer reference, and a later implementer reading it as one would
reintroduce a bug the spec explicitly forbids (§8.1: "Exact-answer constructibility
is not a loss condition").

## Three test collisions the later milestones must honour

Found by reading the suite against the design, before writing code. The suite has
zero style assertions, so **every test that breaks under a reskin encodes a real
behavioural contract** — a break is a signal, never an obstacle.

- **`gameOver` printing the product** collides with `App.test.tsx:242`
  (`getByText("9 × 9 =")`) and `GameOverScreen.test.tsx:43` (`"7 × 8 ="`).
  `getByText` matches the element whose own text equals the string, so the product
  must render as a *sibling* of that paragraph, never inside it.
- **Keeping answer slots mounted through feedback** — which the design requires,
  because the bloom and the crack both play on the submitted tiles — collides with
  `GameScreen.test.tsx:343`, which asserts no `Answer slot` *button* exists in
  feedback. Both hold if the slots render non-interactively outside `answering`:
  the `role="status"` panel already announces the outcome, so a disabled slot
  button in feedback is focus-order noise.
- **The capacity meter** must not carry `.primary` and must not precede Streak, or
  it breaks the two computed-font-size tests and the HUD ordering test.

## Six of the seven "unbuilt" motion refs already have shapes

`decisions.md` listed `7b`, `7c`, `2d`, `8a`, `11a`/`8c`, `10i` and `11C` as
specified but not built, which reads as seven original designs still to make.
`ozterisk Storyboard.dc.html` already carries `sb-rim`, `sb-drop`, `sb-slide`,
`sb-sweep`, `sb-settle` and `sb-stamp`, and `7b`/`7c` turn out to be `sb-ring`
re-used at `.18s` and `.34s` delay rather than new frames. Only `2d`, the six-chip
burst, has to be authored from nothing.

The caveat is a retiming trap: the canvas frames hold across a `2.6s` infinite
loop, so a shape spanning 8%–60% there becomes a dead first tenth and a dead final
40% of a `240ms` one-shot. Each must be renormalised to 0–100% of its useful range,
not merely given a shorter duration.

**A file listing what is missing is not the same as a file listing what does not
exist.** The gap was in the index, not in the work.

## Two things review caught that no gate could

Both were in prose I wrote in this PR, and both passed lint, typecheck, 211 tests
and the production build — because none of those read a markdown file.

**A tier boundary stated in prose is not checked by anything.** §1.12 first said the
middle rack tier starts at `360px` with `66 × 64` tiles and a `12px` gap. Five tiles
plus four gaps is `378px`, so every viewport from 360–377px would have clipped — the
exact failure §8.5's `320px` rule exists to prevent, reintroduced one tier up by the
amendment meant to fix it. The boundary moved to `400px`, and the rule now states the
padding budget at each tier's lower bound so the arithmetic is checkable rather than
implied. Note the design document's own figure was `390px`, which `378px` plus usable
padding also does not fit; the drawn design had the same bug.

**A universal quantifier is a claim, and this one was false.** §1.12 said the
inventory was "the sixteen storyboard moments, each with an assigned duration and
easing". `tokens/motion.css` assigns nothing to `2d`, `7b`, `7c`, `8a`, `8c`, `10i`
or `11a` — seven of the sixteen. An implementer trusting that sentence would have gone
looking for values that do not exist. §1.12 now names the moments and states where
missing timings come from, and `decisions.md` records the gap where an implementer
looks for it.

The shared lesson: **the parts of a specification a build cannot execute are the parts
most worth reviewing.** The token values, the component contracts and the test pins
all have gates. The prose stating how they fit together has none.

## Open follow-ups

- **The 320px rack tier is not designed.** §1.12 now specifies `52 × 64` at `8px`
  gap below `400px`; that is a constraint solved on paper, not a drawn frame.
- **`2d` still needs authoring**, and it is the one ref §1.12's amendment had to
  strike "No particles" for. If it does not survive design review, the clause can
  be narrowed again — that would be a smaller §1.12 than the one merged here.
- **The design directory is 920K**, roughly 500K of which is canvas output kept
  because the storyboard is the only frame-by-frame motion source. What to prune
  once `M5.5f` ships has its own issue rather than a silent decision at the end.
- **`package-lock.json` still lacks the `engines` block** and dirties a fresh
  worktree by three lines. `M5.5b` adds `@fontsource` dependencies and is the
  natural place to fold it in.
