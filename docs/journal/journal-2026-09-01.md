# Journal — 2026-09-01 — how Claude Design and Claude Code actually connect

The M5.5 design pass sent four questions out to Claude Design and got four
answers back. Getting them *into* the repo took most of a session and one wrong
theory, because the two tools connect in a shape neither of us assumed. This
records the topology, the failure it caused, and the merge rule that follows
from it — the parts that are expensive to re-derive.

## Two different things are called a "project"

| | Design **system** project | Design project |
|---|---|---|
| What it is | a file tree — `tokens/`, `components/`, `guidelines/`, preview cards | where the design agent works; holds canvases (`*.dc.html`) |
| Claude Code access | full read/write, via the `DesignSync` tool | **none** |
| Who writes it | `/design-sync`, from the repo | the design agent |
| Role | the **input** the design agent designs with | the **output** the design agent produces |

`DesignSync(list_projects)` returns only the first kind. The second is invisible
to it — not filtered, not permission-gated, simply not that API's subject.

The consequence that cost us the session: **the design agent does not write back
into the design-system project.** The app says so in its own banner — *"To make
changes to the design system, edit your code and re-run /design-sync."* The
design system is a read-only input to it. So when the design agent reports that
it has changed the design system, it means it has changed a design system, in
its own project, which Claude Code cannot see at all.

## The loop, end to end

```
repo docs/design-system/  --/design-sync-->  design-system project
                                                    |
                                            design agent reads it
                                                    v
                                            design project (canvases, edits)
                                                    |
                                            export / download .zip
                                                    v
repo docs/design-system/  <--- diff and merge by hand ---+
```

Every hop is API-mediated except the last one, which is a file download. That
asymmetry is the whole story. The mental model of a Figma MCP — one live
surface both tools read, write, and inspect metadata on — is right about the
outbound half and wrong about the return: **there is no write-back channel, only
an export.**

## The false positive that made this hard to see

Between two `list_files` calls on the design-system project, `updatedAt` moved
from `07:45:32Z` to `09:26:40Z`. Nothing in it had changed: the file list was
identical to the path, and `readme.md`, `github.md`, `tokens/elevation.css` and
`tokens/fonts.css` all came back byte-identical to what we had uploaded.

The timestamp moves when the app re-runs its self-check and rewrites
`_ds_manifest.json` — which happens when somebody opens the project. **A moved
`updatedAt` is evidence the project was viewed, not that its content changed.**
Diff a file to answer that question.

Two independent checks were worth more than either alone: the files we uploaded
could in principle have been stale reads, but `_adherence.oxlintrc.json` is
generated *by the app* from the project's current contents, and it still listed
three font families with no Hangul face. App-generated metadata is the honest
witness to what a project actually holds.

## The merge rule

**Export snapshots branch from whenever the design agent started, and re-import
is a merge, never a copy.** This export was authored from the pre-#59 copy, so
it silently dropped:

- the contract-precedence header in `readme.md` — the statement that
  `docs/spec/ui-i18n.md` §1.12 is the contract and the design system is the
  normative source for the values it refers to;
- the storyboard provenance of the unbuilt motion refs in `decisions.md`, which
  still governs the four that remain (`8a`, `11a`/`8c`, `10i`, `11C` are already
  drawn as `sb-*` keyframes and get ported, not authored).

Neither is a design decision, so neither was the design pass's to overturn, and
nothing in `lint → typecheck → test → build` reads a markdown file. This is the
same silent-failure class recorded in `journal-2026-08-30.md`, arriving by a new
route.

The keep-list for a re-import, generalised:

1. **Repo-only files the export cannot know about** — here `_ds_bundle.js` and
   `previews/`, both built by `scripts/`.
2. **Shared files the design app maintains its own version of.** The three
   `components/*/*.card.html` come back wrapping their demos in
   `<script type="text/babel">`; the repo replaced that with a compiled sibling
   in `e02a046`. Verify the *demo* is unchanged (ours matched the export's
   byte-for-byte) and keep the repo's wrapper.
3. **Repo-side prose edits to files the design agent also owns.** Re-apply after
   the merge, as a separate commit, so review can tell the two apart.

## What the pass returned, and the one thing it did not

Four locks, each with rejected alternatives recorded in `decisions.md` §M5.5b:
`oz-fan` for the `2d` burst, `--outline-socket-lifted` (dashed gold) for the
lifted socket, `--ring-focus` as an inset bezel, and a `:lang(ko)` token
override for Korean.

The dashed socket measures. Gold at 34% over `--well-900` was **1.95:1**; the
dashed rule at 72% is **4.53:1**. That was the finding the pass was sent to fix,
and it fixed it.

**The focus bezel does not, and the pass shipped it without the contrast matrix
that was asked for.** `--ring-focus` changes the ring's *geometry*, not its
*tone* — it is still `--gold-300 #e8cd85`. Measured against every surface the
indicator can land on:

| Surface | | Ratio | |
|---|---|---|---|
| felt field | `--felt-700 #14342a` | 8.69:1 | passes |
| socket well | `--well-900 #081a14` | 11.56:1 | passes |
| vermilion primary | `--verm-600 #b5432f` | 3.55:1 | passes |
| ceramic, highlight end | `--clay-050 #fdf8ec` | **1.47:1** | fails |
| ceramic, shadow end | `--clay-200 #e6d7ba` | **1.10:1** | fails |
| gold toggle segment | `--gold-500 #c9a54a` | **1.51:1** | fails |

The gate is `ui-i18n.md` §1.12, as this repo amended it in #59:

> The focus indicator must reach at least `3:1` contrast against **every**
> surface it can appear on, including the ceramic tile face — a single-tone
> indicator that clears the field but not the tile does not satisfy this.

`--ring-focus` is single-tone and clears the field but not the tile. It fails
that clause by its literal words. Moving the ring inside the object does not
change this: the same gold now sits *on* the ceramic instead of beside it.

The fix is already in the system's own vocabulary: `--ring-focus-onDanger`
composes a second, darker inset line under the gold so the ring never sits
directly on a surface it cannot beat. Generalising that to `--clay-900` — the
engraved-digit ink, already a system colour — gives **11.60:1** on ceramic and
**5.68:1** on the gold segment, and on felt the gold line still carries it at
8.69:1. Every surface passes on one line or the other.

Worth noting the pass rejected the two-tone direction (candidate `5i`) as
reading *"like engineering rather than material"*. That judgement is about the
separator as a visible third element; the `onDanger` composition it shipped is
the same idea made material, and it is the design's own answer.

## For next time

- Ask the design agent for the **export**, not for confirmation that it changed
  the system. The two are unrelated.
- State the verification bar in the prompt and then actually run it. This pass
  was asked for a contrast matrix in numbers, returned prose, and the prose was
  wrong — which is exactly why the bar was set that way.
- Budget the return trip. The outbound is one tool call; the inbound is a
  download, a structural diff, a keep-list, and a re-application commit.
