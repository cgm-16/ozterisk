# 2026-09-02 — M5.5b foundations, measured

Task T32. The roadmap's exit gate for this milestone is four claims and CI proves
none of them: `lint → typecheck → test → build` catches no design regression, and
`global.css` is imported only by `main.tsx` and `gallery/main.tsx`, so it never
enters the test graph at all. Everything below was measured against a production
build served by `vite preview`, at three viewports, in both locales.

## The done-check the plan named does not work

The phase plan asked for `document.fonts.check()` as the evidence that Korean
renders in a Hangul-capable face. It returns a **false positive**. Before the
Korean face had loaded — with `Noto Sans KR` absent from `document.fonts`
entirely — this still returned `true`:

```js
document.fonts.check('16px "Noto Sans KR"', '라운드')   // → true, with no Hangul face present
```

The API answers "can this text be rendered", counting fallbacks, not "is the face
I named available". So it would have returned `true` in exactly the failure state
D2 was written to catch: every Korean string silently falling through to
`system-ui`. Had this milestone shipped that check as its gate, the gate would
have passed on a broken build.

What works is measuring rendered width against a deliberately absent family:

| `font-family` used to render `라운드 점수 연속 정답` at 64px | width |
|---|---|
| `"Noto Sans KR"` | **583.69px** |
| `"NoSuchFace-ozterisk"` (falls through to the default) | 548.75px |
| `var(--font-ui)` — the app's real stack | **583.69px** |

The app's stack matches the explicit Noto measurement and differs from the
fallback, so Hangul genuinely resolves to Noto Sans KR — Zen Kaku Gothic New is
tried first and correctly passes Hangul through per glyph. `FontFace.status` is
`"loaded"`, and `Noto Sans KR 400` appears in `document.fonts` **only after** the
locale switch, which is the other half of the claim: English never pays for it.

Generalisable: an API that reports whether an *outcome* is achievable is not
evidence about the *mechanism* you built. Ask it to distinguish your mechanism
from its own fallback, and if it cannot, measure something that can.

## Zero non-origin requests

Full English load plus a locale switch to Korean: **zero** requests to any origin
other than the app's own. Verified by filtering the network log, and verified
that the log was populated rather than the filter broken — the same log shows the
four font fetches, all `localhost:4173/assets/`.

Static scan agrees: the only literal `http(s)://` strings anywhere in `dist/` are
XML namespace identifiers (`www.w3.org/2000/svg`, `xlink`, MathML) and React's
`https://react.dev/errors/` message-builder string. None is ever fetched.

## Weight per locale

Only `.woff2` is fetched by any current browser; `@fontsource` ships `.woff`
beside it and Vite emits both, so disk and network differ and both belong here.

| | network (woff2) | on disk (incl. `.woff`) |
|---|---|---|
| English ceiling — 9 Latin faces | 145 KB | 331 KB |
| Korean adds — Noto Sans KR 400 | 529 KB | 1,359 KB |

The English figure is a ceiling, not a first-load cost: the title screen fetched
only 2 of the 3 Zen Kaku weights, because a face nothing renders is never
requested.

**The `.woff` duplicates are ~1.0 MB of `dist/` that no browser fetches.** Not a
network cost and not this milestone's gate, so nothing was done about it, but it
is a real deploy-size decision someone should take deliberately rather than
inherit.

Korean at 529 KB is why only weight 400 ships. Three weights measured 1.62 MB
against the plan's ~1 MB line; bold Hangul is browser-synthesised.

## The keyframes reached the document

The failure the whole partial layout exists to prevent: CSS Modules scope
`@keyframes` names, so an animation naming a scoped keyframe fails silently. All
ten enumerate as `CSSKeyframesRule` in `document.styleSheets` —

`oz-bloom`, `oz-counter-fall`, `oz-counter-zero`, `oz-crack`, `oz-dust`,
`oz-fan`, `oz-fire`, `oz-ring`, `oz-rise-ready`, `oz-round-rise`

— so the names are global and every later phase can reference them. Worth
repeating because it is invisible to every other gate: nothing in lint,
typecheck, test or build would have failed if these had been scoped away.

## Focus, and the tiers

`--ring-focus` resolves in the browser to
`inset 0 0 0 2px #e8cd85, inset 0 0 0 3px #16352b` — the two-tone bezel settled
on 2026-09-01. Its ratios were computed from the committed token values then and
are not re-derived here.

No horizontal scroll at any tier, in either locale: `scrollWidth` equals
`clientWidth` at 320, 400 and 1024, and a sweep for any element whose right edge
exceeds the viewport returned empty.

| viewport | `--tile-w` | `--tile-h` | `--rack-gap` | rack = 5w + 4g |
|---|---|---|---|---|
| 320px | 52px | 64px | 8px | 292px |
| 400px | 66px | 64px | 12px | 378px |
| 1024px | 64px | 80px | 12px | 368px |

Every tier clears the 44×44 target minimum, and each rack fits its tier's lower
bound as §1.12 requires.

## Stated as unmeasured

- **"The rack holds ten sockets at every tier" is not verified.** The tier tokens
  are correct at all three viewports, but no component rule consumes them yet —
  scanning the live stylesheets for `--tile-w`/`--tile-h`/`--rack-gap` outside
  `:root` returns only the two media queries that define them. `TileInventory`
  wears them in M5.5d, and that is where the claim becomes checkable.
- **`prefers-reduced-motion` neutralisation is not verified.** The block is
  present and ported, but nothing is animated yet, so there is no motion to
  observe being removed. M5.5f wires the animations; M5.5g walks it, following
  the technique in `journal-2026-08-09.md` — flip `rule.media.mediaText` and read
  `getComputedStyle`, rather than touching OS settings.
