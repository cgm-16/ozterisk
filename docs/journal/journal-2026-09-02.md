# 2026-09-02 — M5.5b foundations, measured

Task T32. The roadmap's exit gate for this milestone is four claims and CI proves
none of them: `lint → typecheck → test → build` catches no design regression, and
`global.css` is imported only by `main.tsx` and `gallery/main.tsx`, so it never
enters the test graph at all. Everything below was measured against a production
build served by `vite preview`, at three viewports, in both locales.

## The done-check the plan named does not work

The phase plan asked for `document.fonts.check()` as the evidence that Korean
renders in a Hangul-capable face. It returns a **false positive**. Before the
Korean face had loaded — with `Noto Sans KR` absent from `document.fonts`
entirely — this still returned `true`:

```js
document.fonts.check('16px "Noto Sans KR"', '라운드')   // → true, with no Hangul face present
```

The API answers "can this text be rendered", counting fallbacks, not "is the face
I named available". So it would have returned `true` in exactly the failure state
D2 was written to catch: every Korean string silently falling through to
`system-ui`. Had this milestone shipped that check as its gate, the gate would
have passed on a broken build.

What works is measuring rendered width against a deliberately absent family:

| `font-family` used to render `라운드 점수 연속 정답` at 64px | width |
|---|---|
| `"Noto Sans KR"` | **583.69px** |
| `"NoSuchFace-ozterisk"` (falls through to the default) | 548.75px |
| `var(--font-ui)` — the app's real stack | **583.69px** |

The app's stack matches the explicit Noto measurement and differs from the
fallback, so Hangul genuinely resolves to Noto Sans KR — Zen Kaku Gothic New is
tried first and correctly passes Hangul through per glyph. `FontFace.status` is
`"loaded"`, and `Noto Sans KR 400` appears in `document.fonts` **only after** the
locale switch, which is the other half of the claim: English never pays for it.

Generalisable: an API that reports whether an *outcome* is achievable is not
evidence about the *mechanism* you built. Ask it to distinguish your mechanism
from its own fallback, and if it cannot, measure something that can.

## Zero non-origin requests

Full English load plus a locale switch to Korean: **zero** requests to any origin
other than the app's own. Verified by filtering the network log, and verified
that the log was populated rather than the filter broken — the same log shows the
four font fetches, all `localhost:4173/assets/`.

Static scan agrees: the only literal `http(s)://` strings anywhere in `dist/` are
XML namespace identifiers (`www.w3.org/2000/svg`, `xlink`, MathML) and React's
`https://react.dev/errors/` message-builder string. None is ever fetched.

## Weight per locale

Only `.woff2` is fetched by any current browser; `@fontsource` ships `.woff`
beside it and Vite emits both, so disk and network differ and both belong here.

| | network (woff2) | on disk (incl. `.woff`) |
|---|---|---|
| English ceiling — 9 Latin faces | 145 KB | 331 KB |
| Korean adds — Noto Sans KR 400 | 529 KB | 1,359 KB |

The English figure is a ceiling, not a first-load cost: the title screen fetched
only 2 of the 3 Zen Kaku weights, because a face nothing renders is never
requested.

**The `.woff` duplicates are ~1.0 MB of `dist/` that no browser fetches.** Not a
network cost and not this milestone's gate, so nothing was done about it, but it
is a real deploy-size decision someone should take deliberately rather than
inherit.

Korean at 529 KB is why only weight 400 ships. Three weights measured 1.62 MB
against the plan's ~1 MB line; bold Hangul is browser-synthesised.

## The keyframes reached the document

The failure the whole partial layout exists to prevent: CSS Modules scope
`@keyframes` names, so an animation naming a scoped keyframe fails silently. All
ten enumerate as `CSSKeyframesRule` in `document.styleSheets` —

`oz-bloom`, `oz-counter-fall`, `oz-counter-zero`, `oz-crack`, `oz-dust`,
`oz-fan`, `oz-fire`, `oz-ring`, `oz-rise-ready`, `oz-round-rise`

— so the ten definitions reached the document unscoped. That is the definition
half of the claim and no more: nothing in `src/` declares an animation yet, so
whether a component's own rule can reference one of these names is untested,
and it is listed below as unmeasured. Worth repeating because it is invisible
to every other gate: nothing in lint, typecheck, test or build would have
failed if these had been scoped away.

## Focus, and the tiers

`--ring-focus` resolves in the browser to
`inset 0 0 0 2px #e8cd85, inset 0 0 0 3px #16352b` — the two-tone bezel settled
on 2026-09-01. Its ratios were computed from the committed token values then and
are not re-derived here.

No horizontal scroll at any tier, in either locale: `scrollWidth` equals
`clientWidth` at 320, 400 and 1024, and a sweep for any element whose right edge
exceeds the viewport returned empty.

| viewport | `--tile-w` | `--tile-h` | `--rack-gap` | rack = 5w + 4g |
|---|---|---|---|---|
| 320px | 52px | 64px | 8px | 292px |
| 400px | 66px | 64px | 12px | 378px |
| 1024px | 64px | 80px | 12px | 368px |

Every tier clears the 44×44 target minimum, and each rack fits its tier's lower
bound as §1.12 requires.

## A token can be correct and worn by nothing

`--ring-focus` is the two-tone bezel, its ratios are right, and **nothing wears
it.** `grep -rn 'ring-focus' src/` returns its definition in
`tokens/elevation.css` and no consumer at all. The indicator the app actually
ships is the single rule in `global.css`, and it was drawing one gold line at
`outline-offset: -2px` — *inside* the control, on the control's own face.

Step 4 of the plan asked for the ratios "computed from the committed token
values", so it was satisfiable without looking at a rendered pixel, and that is
how it was satisfied: the token was measured, the shipped rule was not.

Gold `--gold-300` `#e8cd85` against each surface, re-derived from the hex
values rather than cited from the token file:

| surface | token | ratio |
|---|---|---|
| surround — what `body` actually paints | `--felt-900` `#071711` | 11.85 |
| socket | `--well-900` `#081a14` | 11.56 |
| panel, modal, rail | `--felt-800` `#0b211b` | 10.82 |
| the felt itself | `--felt-700` `#14342a` | 8.69 |
| raised felt | `--felt-600` `#1b4436` | 7.01 |
| **ceramic tile face** | `--clay-200` `#e6d7ba` | **1.10** |
| **primary button face** | `--gold-500` `#c9a54a` | **1.51** |

Every ground clears 3:1. The two failures are both element *faces*, and both
are focusable: every inventory tile is a `<button>` wearing `--surface-tile`,
and the primary button of every screen — start, submit, play again, and the
overflow action — wears `--accent`. On `main` the same rule carries
`outline-offset: 2px`; this milestone flipped the sign.

The fix is `outline-offset: 2px` again. Walked with Tab and never with a click —
a mouse-focused control does not match `:focus-visible`, so a click-then-measure
returns the same blank as a missing ring — over every focusable control on every
reachable screen at 320, and over the rack and the answer slots again at 400 and
1024: 111 focus measurements. On all of them the outline computes to
`solid 2px 2px rgb(232, 205, 133)`, the ring
occupies exactly the 2–4px band on all four edges, and no ancestor anywhere sets
a non-`visible` `overflow`. Each band was read from screenshot pixels — the
focused image against the unfocused image at the same coordinates — because a
computed background cannot see what the fix turns on.

**It does not put the ring on the ground in every case.** It does on every
control except the inventory tile:

| control | own face | what the outer band lands on | ratio |
|---|---|---|---|
| `How to Play`, both `LanguageToggle` segments, an answer slot, `Clear`, `Share`, `Copy Result` | transparent or `--felt-800`; the slot swaps to `--well-900` under focus | ground — `--felt-900` `#071711` | 11.85 |
| `Start Run`, `Submit`, `Next Round`, `Play Again` | `--accent` | ground — `--felt-900` `#071711` | 11.85 |
| inventory tile, left and right edges | `--surface-tile` | ground, darkened by the neighbouring tiles' contact shadows — `#06140f` | 12.11 |
| **inventory tile, bottom edge — every tile, every tier** | `--surface-tile` | **the tile's own `--shadow-tile` ceramic edge: `--clay-400` `#b3a184` bare, `#b09e81`/`#b19f82` where the next row's contact shadow darkens it** | **1.62–1.68** |
| **inventory tile, top edge — wherever a tile overlaps it directly above** | `--surface-tile` | **the upper tile's ceramic edge, `#ae9d80`, over the outer 1px of the band** | **1.70** |

`--shadow-tile` is `0 5px 0 var(--clay-400), 0 10px 18px …`: no blur, no spread,
5px down, so the ceramic thickness occupies exactly the 0–5px strip beneath each
tile and the ring's 2–4px band is entirely inside it. The unfocused pixel column
under a tile reads `#b3a184` at 0.5, 1.5, 2.5, 3.5 and 4.5px out and reaches
felt only at 5.5px. Nothing else in the app paints within 4px of a control: the
tightest neighbours that paint anything are 8px away (toggle segments, answer
slots, tiles) and 12px (`Submit`/`Clear`, the three game-over actions), against a
band that ends at 4px, so no ring lands on a neighbour's *face* anywhere —
including on any `--accent` one, which was the failure this walk went looking
for. The top-edge reading is the same shadow from below: the rack gap is 8px and
the shadow reaches 5px, so it covers 3–8px above the tile beneath and takes the
outer 1px of that tile's band.

That also corrects the earlier figure. `#071711` — 11.85 was recorded for a
focused *tile*, and it is the ground behind the tile, not what is within 4px of
its edges; the tile's own shadow sits in between.

Both readings are viewport-independent, because the rack is: `TileInventory`
sets `min-width`/`min-height: var(--target-min)` and `gap: var(--space-2)`, not
the tier tokens, so the tile measures 44×44 with an 8px gap at 320, 400 and 1024
alike — larger only when it carries a `NEW` or discard badge, which stretches it
in the discard phase without changing the gap or the shadow. What the tier
changes is the wrap — 5 tiles per row at 320, 7 at 400, all ten in one row at
1024 — and that decides only whether the 1.70 top-edge reading exists at all.
The 1.62–1.68 bottom-edge reading is on every tile at every tier.

Two smaller things the pixels show and the computed styles do not. `.tile` is
`position: relative`, so a later sibling paints over an earlier one's outline: a
focused tile's right-hand ring is dimmed by the next tile's blurred contact
shadow from `#e8cd85` to `#c8b072`, which still reads 9.14 against its backdrop
but is not the token colour. And `AnswerSlots.module.css`'s own `:focus-visible`
rule is not an opt-out — it sets `border-color` and `background` and never
`outline`, so a focused slot computes the same `solid 2px 2px rgb(232, 205, 133)`
and reads 11.85 on all four edges.

The tile's residual is accepted here and left to M5.5d, which is where its fix
already lives. `--ring-focus` is inset and two-tone for exactly this surface:
gold cannot clear the ceramic face at all, and the `--clay-900` line reads 9.37
against it. It is a `box-shadow`, so it has to compose after the tile's own
shadow — `box-shadow: var(--shadow-tile), var(--ring-focus)` — which is a rule
in `TileInventory.module.css`, and this milestone restyles no component. The
only fix that would fit inside M5.5b is pushing the offset past the shadow's
5px, which invents a geometry the design never asked for and leaves 1px of the
8px rack gap.

The two are not the same defect at different strengths. The one this section
opens with put 1.10 on all four edges of a ring drawn inside the face, which is
no visible indicator; what is left is three edges between 11.85 and 12.11 and
one at 1.62, which is an indicator that reads. M5.5d inherits it as a
requirement rather than as a surprise: the tile is the control whose focus
treatment the global rule cannot finish.

Not covered, and why:

- **`src/gallery/` is excluded.** It is a development surface, not a §8.5 gate.
- **`OverflowControls`' confirm button cannot be reached** — so the `--accent`
  inventory above overcounts by one; there is no overflow action to focus. It
  renders only when `requiredCount > 1`, and with `INVENTORY_CAPACITY = 10` and
  `REWARD_BONUS = 1`
  a correct answer returns exactly one tile more than it spent, so the inventory
  never exceeds 11 and `getOverflowCount` never exceeds 1. Reaching the overflow
  phase confirms the consequence rather than inferring it: the rendered
  component is `<div><p>Choose 1 tile(s) to discard.</p></div>` and nothing more.
  Its `<p>` sibling is not focusable, so the phase contributes no control of its
  own — only the rack in discard mode, which is in the table above.

Generalisable, and the reason Step 4 changed too: **a token that is defined but
unconsumed passes every guard built to catch a token that is undefined.** T29's
dangling-`var()` grep, lint, typecheck, test and build all see a healthy token.
It is the same shape as the `.reward` defect fixed in `05edfbf` — a correct
surface token with no ink token paired to it — and it is why the fix is not
only the value: a step that reads a definition cannot see what is worn.

## Stated as unmeasured

- **"The rack holds ten sockets at every tier" is not verified.** The tier tokens
  are correct at all three viewports, but no component rule consumes them yet —
  scanning the live stylesheets for `--tile-w`/`--tile-h`/`--rack-gap` outside
  `:root` returns only the two media queries that define them. `TileInventory`
  wears them in M5.5d, and that is where the claim becomes checkable.
- **An `oz-*` name resolving from a component's scope is not verified.** The
  enumeration above settles the definition half — the ten names reached the
  document unscoped. The reference half is a `.module.css` rule naming one of
  them and the name surviving the module rewrite, and it needs a component that
  declares an animation; none does. M5.5f wires the first one, and that is
  where the claim becomes checkable.
- **`prefers-reduced-motion` neutralisation is not verified.** The block is
  present and ported, but nothing is animated yet, so there is no motion to
  observe being removed. M5.5f wires the animations; M5.5g walks it, following
  the technique in `journal-2026-08-09.md` — flip `rule.media.mediaText` and read
  `getComputedStyle`, rather than touching OS settings.
