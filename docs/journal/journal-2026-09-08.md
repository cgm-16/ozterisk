# 2026-09-08 — M5.5f opens: four rulings before a line of motion is wired

`M5.5e` merged as `b6e801b`. `M5.5f` is the phase that makes the sixteen named
moments actually play.

## The finding that shapes the phase

`src/styles/tokens/keyframes.css` has defined ten of the sixteen since `M5.5b`,
and **not one of them is referenced anywhere in `src/`.** The vocabulary landed
four phases ago; nothing speaks it. So this is not a phase that tunes motion —
it is a phase that turns it on for the first time, and the risk profile follows
from that.

The risk is the silent-failure class already recorded in
`journal-2026-08-09.md`: an `animation:` naming a keyframe the stylesheet does
not define fails with no error, no warning and no motion. A phase whose entire
content is `animation:` declarations has that as its dominant failure mode, and
a screenshot of it looks exactly like a resting state. `T50` therefore lands
every remaining keyframe **first, alone**, and adds a static guard asserting
that every animation name used in `src/` is one the stylesheet defines.
`keyframes.css` is one shared file; five wiring tasks editing it in parallel is
a merge conflict by construction.

## Ruling 1 — #93, and how much of it is actually a problem

`SUBMIT_CORRECT` sets `phase: getOverflowCount(nextInventory) > 0 ? "overflow"
: "feedback"`, so a correct answer whose reward pushes the rack past ten skips
`feedback` entirely. `T46` mounted the read-only slots for `answering` and
`feedback` only. The issue reads as *the reward motion has nowhere to play on
that path*.

It is narrower than that. Checking where the design system itself mounts each
moment settles it:

| Moment | Design mounts it on | Mounted in `overflow`? |
|---|---|---|
| `9i` reward fire | `TileInventory.jsx:66` — the rack | **yes** |
| `2a` bloom | `AnswerSlots.jsx:106` | no |
| `7a`/`7b`/`7c` rings | `AnswerSlots.jsx:94` | no |
| `2d` burst | `AnswerSlots.jsx:125` | no |

So the reward tiles fire on **both** paths, because `9i` was always the rack's
moment — *"fires in place, in sorted position"* is a description of the rack's
sort order, not of the verdict panel. Only the four slot-bound moments are
affected.

**Ruling: option 2 for `9i`, option 3 for the rest.** `9i` mounts on the rack's
`isNew` tiles and plays on every correct answer. `2a`, `7a`/`7b`/`7c` and `2d`
do not play on an overflowing correct answer, and that is recorded in the
inventory rather than worked around.

*Why not option 1 — mount the slots in `overflow` too.* It would put a
verdict's celebration on screen while the player is being asked to destroy a
tile. `decisions.md` treats discard as destructive and irreversible and gives
it three simultaneous cues for exactly that reason; adding a six-chip burst
beside it competes with the one decision the phase exists to ask for. And the
player's attention on that path already belongs to the rack — which is where
the reward is firing and where the discard is chosen.

*Cost if wrong:* on the rounds that overflow, the streak ladder is invisible.
That is a real loss at streak 8, which is rare by construction.

## Ruling 2 — `8a` is positional, not a per-tile identity

*"The eleventh tile rim-rejects, perches on the rail"* presumes something
marking which tile did not fit. `M5.5e` ruled `perchedTile` dropped, because
`SUBMIT_CORRECT` merges all N+1 reward tiles through `sortTiles` and nothing
identifies the overflowing one. `isNew` marks every arriving reward tile, not
that one.

But `TileInventory` renders `Math.max(INVENTORY_CAPACITY, tiles.length)` cells,
so **cell index 10 exists only while the rack overflows.** The eleventh
*position* is real even though the eleventh *tile* is not.

**Ruling: `8a` animates the eleventh cell, whatever tile sorts into it.** No
`src/game/` change, no invented identity, and no claim the code cannot support.

## Ruling 3 — `9b` needs a keyframe here, and that is not an amendment

`decisions.md` records `9b` as *"built — transition, not a keyframe."* That is
true of the design, whose tile travels from rack to slot. It is not true of
this codebase: `M5.5d` made the rack ten fixed sockets and a selected tile
keeps its socket, so the tile in the answer slot is a **separate element that
mounts**. A transition on a mounting element does nothing.

§1.12 already covers the assignment — *"A moment whose duration and easing are
not yet assigned … gets them assigned by the milestone that implements it, and
that assignment is not an amendment."* The moment, its duration (`--dur-select`)
and its easing (`--ease-settle`) are unchanged; only the mechanism differs, and
the mechanism differs because our architecture is the one the design asked for.

## Ruling 4 — `10i` is deferred, and it is a product question, not a motion one

*"Game over: the last tiles are swept off the rack."* The storyboard frame for
it (`phase: "game over"`) still draws the rack and the equation on screen. Ours
does not: `App` swaps `GameScreen` for `GameOverScreen`, and `GameOverScreen`
has no rack.

Implementing it needs either `GameScreen` to outlive its own phase — App-level
orchestration for one decorative moment on a screen the player is leaving — or
`GameOverScreen` to grow a rack, which is new product surface and would need
`product.md` §1.10 amended. `M5.5f` is not a docs phase.

**Ruling: `10i` is not built. Filed as #104, with its reason, and recorded in the
inventory.** The exit gate says every moment implemented, so `M5.5f` will miss
part of its gate. That is stated rather than papered over — the precedent is
`M5.5b`, which missed the ceramic focus reading and left the gate as written
because the gate was the standard and the phase fell short of it.

`8c` is the same class of problem — a tile that leaves state unmounts, and CSS
cannot animate an unmounted node — but its fix is contained: `TileInventory`
holds the departing tile and drops it on `animationend`, which needs no timer
and needs nothing outside the rack. So `8c` is built and `10i` is not, and the
difference is blast radius, not effort.
