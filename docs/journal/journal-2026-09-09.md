# 2026-09-09 — M5.5f measured: fifteen moments, one dead, and a ruling built on a false premise

`T56`. Measured in-page against the dev server at `localhost:5174`, in the
gallery and in a live run. Narrative is not evidence, so every row below is a
figure.

## The two traps that shaped the method

**`playState: "running"` is not evidence anything ran.** The automation tab is
backgrounded — `document.hidden === true` — so the document timeline never
advances. `document.timeline.currentTime` read `0`, then `0` again 200ms later.
Every animation on the page reports `currentTime: 0` and `playState: "running"`
indefinitely. A walk that collected those two fields would have "verified"
sixteen moments without proving a single one produces motion.

What replaced it: **seek each animation across its own span and read the
element's resolved style at each stop.** `a.currentTime = duration * f` for
`f` in `0, 0.5, 1`, re-reading `getComputedStyle` at every stop because it is
stale within one `evaluate`. An animation that resolves but moves nothing —
a `transform` on an inline box, a zero-size node, a name that matched no
keyframe — reads identical at all three. This is stronger than watching the
clock: it proves the keyframes reach the element, and it is immune to the
frozen timeline.

**A transition cannot be read the same way.** Under a frozen timeline a
transitioning property returns its start value forever: the enabling Submit
button read `translateY(4px)` before *and* after `disabled` flipped. The
reading that works is the pair of resting targets with transitions suppressed
(`* { transition: none !important }`), which is what the transition
interpolates between.

## Defect — `8c` is implemented and unreachable

Confirming a discard plays nothing. No `oz-tip-off`, no `.cellDeparting` in the
document, measured 20ms after the click on a frozen timeline where a held
element could not yet have retired itself. Fixed in this branch; #105 covers the
gallery gaps found alongside it.

Root cause is in `GameScreen`, not in the moment:

```tsx
dispatch({ type: "TOGGLE_DISCARD", tileId });
if (getOverflowCount(state.inventory) === 1) dispatch({ type: "CONFIRM_DISCARD" });
```

Both dispatches are in one click handler, so React batches them into a single
update. `TileInventory` never renders a state where `pendingDiscards` holds the
tile — the rack goes straight from "not marked" to "gone". `T53`'s detection
asks `previous.pendingDiscards.includes(tile.id)`, which is therefore never
true.

**And this is the only discard path that exists.** `INVENTORY_CAPACITY` is 10
and `REWARD_BONUS` is 1, so `getOverflowCount` never exceeds 1 and the
two-step path through the Confirm Discard button is unreachable — already
journaled, in a different context, as "OverflowControls' confirm button is
unreachable".

The predicate that works is available without new props: a tile that vanishes
while the *previous* render had `mode === "discard"` left by discard. That
does not depend on ever having observed `pendingDiscards`. Filed; `T53`'s
component owns it.

## Correction — #93's premise is false, and my ruling rested on it

Issue #93 states: *"a correct answer that overflows never enters feedback, so
the bloom has no slots to play on."* I ruled on that on 2026-09-08 without
checking it, and recorded a cost: the streak ladder is invisible on rounds that
overflow.

Measured, on the first correct answer of a fresh run:

```
answering → (Submit) → overflow → (discard) → feedback
```

`gameReducer.ts:128-137`, `CONFIRM_DISCARD`, sets `phase: "feedback"`. The
overflow path does not skip feedback; it **defers** it by one step. `oz-bloom`
fired ×2 on the submitted tiles after the discard, and at streak 3 the jade
ring fired with it.

I read `SUBMIT_CORRECT`'s ternary, saw `overflow`, and stopped. The branch that
answers the question is fourteen lines further down the same file. `T46` found
the symptom and reported it accurately; the premise it inferred was wrong, and
I confirmed the inference instead of the code.

**What survives:** nothing needs rebuilding. `9i` on the rack was ruled correct
for a reason that still holds — the design mounts it there, and it now measurably
fires in both phases. The slot-bound moments play in `feedback` as they always
would.

**What was wrong:** the recorded cost. There is none. The issue should be closed
as not-a-defect rather than accepted, and `decisions.md`'s `9i` row should stop
implying the overflow path is a special case that needed rescuing.

Worth stating plainly, because it is the transferable lesson: the ruling was
made carefully, argued from the design system, and cross-checked against where
the design mounts each moment — and it was still built on an unverified
sentence. Checking the design was not a substitute for checking the reducer.

## Reduced motion, both directions

Flipping `rule.media.mediaText` between `'all'` and
`'(prefers-reduced-motion: reduce)'`:

| Read | under `reduce` | under normal |
|---|---|---|
| `--press-offset` | `0px` | `2px` |
| `.crack` animation-duration | `1e-05s` | `0.52s` |
| `Tile` transition-duration | `1e-05s` | `0.13s, 0.13s` |
| `ActionButton` transition-duration | `1e-05s` | `0.1s, 0.1s, 0.15s` |

Both directions matter and only both together mean anything: `global.css`
neutralises everything with `!important`, so a `reduce` reading alone cannot
tell a wired animation from an unwired one — a component with no motion passes
that half of the gate.

**The press/state distinction holds.** `11d`'s resting offset is a literal, not
`--press-offset`, and it survives:

| | under `reduce` | under normal |
|---|---|---|
| disabled, at rest | `translateY(4px)` | `translateY(4px)` |
| enabled, at rest | `translateY(0)` | `translateY(0)` |

The offset survives; the transition into it is neutralised. That is the correct
split — "not yet" reads as "not raised" whatever the motion setting, exactly as
a marked tile keeps its lift and tilt. `global.css`'s claim that zeroing one
token retires every press in the app is accurate: nothing this phase added is a
press.

*Carried:* `motion.css` names no resting-offset token, which is why that `4px`
is a literal. A `--rise-offset` would be its right home.

## Traps carried forward

- `document.hidden` freezes the document timeline: `currentTime` never advances
  and `playState` reads `"running"` forever. Seek, do not watch.
- A transitioning property reads its start value under a frozen timeline. Read
  the two resting targets with transitions suppressed instead.
- `getComputedStyle` is stale within one `evaluate` — re-read at every stop.
  (From `T37`; hit again here.)
- `getBoundingClientRect` taken after seeking reports the *seeked* box, not the
  resting one. The 213px ring and 147×184 dust above are peak extents, and are
  labelled as such.
- jsdom substitutes no custom properties and expands no `transition` shorthand.
  (From `T53`.)
- A window resize does not take on a backgrounded tab — `innerWidth` stayed
  1920 after resizing to 320. A fixed-width iframe gives a real layout viewport
  and, usefully, a scrollbar that takes layout width.

## Review round — the one code finding was a pivot, not a frame

Codex and CodeRabbit between them raised five findings on #106. Two were
substantive and one of those touched `src/`.

**`8a` was half-ported.** `oz-rim-reject` carries the storyboard's frames
faithfully, but the storyboard puts `transform-origin: 0 100%` *on the element*
rather than in the keyframe — `Storyboard.dc.html:143`, inline beside
`animation:sb-rim`. Porting the frames and dropping the origin leaves the tile
rotating around its centre, so the moment reads as a swivel rather than as a
tile catching on its lower-left edge. It is the only `transform-origin` in the
whole storyboard, which is exactly why it was easy to lose: nothing else in the
port needed the reflex.

The pivot widens the element's rightward reach, so it owed a `320px` check. It
did not need a measurement. `--rack-columns` is `5` with no breakpoint override
(`spacing.css:38`), and ten sockets fill two rows exactly, so **the eleventh
cell is always alone in the leftmost column of a third row** — four empty
tracks to its right at every tier. The reach lands in empty grid.

Reading the grid was the cheaper gate here, and the stronger one: a sweep
proves the widths I sampled, the column count proves every width.

**A false premise leaves copies.** #93's premise was corrected in
`journal-2026-09-08.md` and on the issue, but `T52` still told its operator
*"the run goes straight to `overflow` … so none of this plays"* — unmarked, and
read as an instruction rather than as a dated belief. Corrected in place, in
the same blockquote form.

Worth carrying: correcting a ruling is not finished when the ruling is
corrected. The premise had been quoted into a task file, and the search that
finds those is for the *sentence*, not for the issue number.

**Two of `T56`'s acceptance criteria could not be met by `T56`.** Per-moment
reduced-motion readings and a `320px` sweep with the high tiers in flight both
need fixtures the same task forbids itself from adding. Codex read that as a
verification signed off short. It is narrower and duller: the criteria were
written stricter than the scope. Named in the task so `M5.5g` — which owns #105
and #85 — inherits the gap rather than the ticks.

I first counted a third, and it was mine, not the task's: I read *"every
deferral carrying an issue number"* as owing one issue each and called the
shared #105 a gap. CodeRabbit pushed back and is right — #105 names `2d`, `7b`
and `7c` outright, and carries their unmeasured peak extents with them. The
criterion was already met; what it was not was *legible*, since the number sat
two sections below the rows. It now sits on the rows.

An invented-stricter reading of one's own acceptance criterion is a failure
mode worth naming. It looks like rigour and it costs the same as a missed
criterion: it puts a phantom on `M5.5g`'s docket.

**Not taken: implement `10i`.** Ruling 4 stands. It needs product surface the
game-over screen does not have, `decisions.md:46` already carries #104, and the
missed gate is declared rather than papered over — the `M5.5b` precedent.
