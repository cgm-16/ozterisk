# 2026-09-18 — the font payload, measured instead of assumed

#64 asked whether the `.woff` duplicates are worth removing and said nobody had
checked what they actually cost. They have now been checked, against production,
and the answer retires the question: they cost nothing a player pays.

The same measurement turned up two faces in the identical category that #64 does
not mention, and corrected one reading I very nearly wrote down wrong.

## Instrument

Playwright Chromium, fresh context per run so nothing is cached, viewport
`390 × 844`, against `https://ozterisk.vercel.app/` serving
`index-D2iZW2u2.js` / `index-DZFHdi4c.css` — the `bae276a` release build. Every
response body sized with `response.body().length`; face status read from the
document's own `FontFaceSet` after `await document.fonts.ready`, not from
`document.fonts.check()`, which answers from the system's installed fonts and
produced a false pass here yesterday.

324,742 bytes decoded. The two text assets are served brotli — 70,933 B of JS
and 6,056 B of CSS — so the real transfer is roughly 157 KB.

**`.woff` requests: 0. `.woff2` requests: 5.** Every `@font-face` lists `woff2`
first and `woff` second, and a browser takes the first format it supports and
stops. Deleting the ten `.woff` files would take about 1.0 MB off `dist/` and
change the waterfall by zero bytes.

So #64 is a deploy-size decision and can never be anything else. Its own body
says as much; what was missing was the reading, and the reading agrees.

## There is no loading-speed problem to find

`<div id="root">` ships empty, so nothing paints until the JS parses and React
mounts — the one structural fact that could plausibly hurt. Measured both ways:

| | first paint | first contentful paint | load |
|---|---|---|---|
| unthrottled | 60 ms | 112 ms | 73 ms |
| Slow 4G + 4× CPU | 404 ms | **840 ms** | 734 ms |

Slow 4G is `Network.emulateNetworkConditions` at 1.6 Mbps down / 150 ms RTT with
`Emulation.setCPUThrottlingRate: 4`. Sub-second FCP on a throttled mid-range
phone is not a problem worth a milestone, and the unthrottled figure alone would
not have been evidence of that — it is the throttled run that settles it.

All nine faces are `font-display: swap`, so fonts never block paint either.

## Two faces nothing can ever request

Every rule using `--font-mono` pairs it with `--weight-medium`:

- `CapacityMeter.module.css:9`
- `GameOverScreen.module.css:45`
- `GameOverScreen.module.css:65`

`--weight-medium` is `500`. `fonts.css` eagerly imports IBM Plex Mono at 400,
500 and **600**, so two of those three faces are selectable by no rule in `src/`
at all — 14,708 and 15,620 bytes of `woff2`, plus their `.woff` twins. This is
#64's category exactly, and it is provable by grep rather than by walking every
phase, because a weight no rule names cannot be selected from any of them.

EB Garamond 400 is also unloaded across title and arena, but it is **not** in
the same bucket and should not be filed as if it were: `GameHud.module.css:32`
and `GameOverScreen.module.css:76` set `font-family: var(--font-numeral)` with
no weight, so they inherit one, and the game-over screen was not walked. Two
screens of evidence is not an app-wide claim.

## The instrument error worth keeping

The first arena run reported IBM Plex Mono never fetched, which would have made
all three weights dead. It was wrong, and the shape of the error is the reusable
part.

That run collected fonts from `page.on("response")` and waited on
`waitForLoadState("networkidle")` after entering the arena. Font requests are
triggered by layout, so the request had not started when idle fired; the context
closed before the response event did. Reading `document.fonts` directly showed
`IBM Plex Mono 500 loading` — present, just not yet answered.

**`networkidle` is not a fence for anything layout triggers.** It reports the
absence of in-flight requests, which is indistinguishable from the moment before
a request begins. The cure is to assert on the thing itself — `document.fonts`
after `fonts.ready` — rather than on a proxy for quiet.

Same family as yesterday's transitioning focus ring and `T56`'s frozen
`document.timeline`: the measurement lands next to the event rather than on it,
and it fails in the direction that looks like a real defect.
