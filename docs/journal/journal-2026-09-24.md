## The freeze this found

The first scripted attempt hung on my own bug: its discard picker chose the
same tile twice, so the second click took the first mark back. Fixed to pick
distinct tiles, the second attempt stopped dead after the second submission
of both Classic runs (English and Korean): the two-tile discard applied, and
the round never advanced. With no Next Round after a discard, nothing could
move it.

Cause: two tiles discarded together finish their 8c exit in the same frame,
and React batches the state updates their `animationend` handlers make.
`TileInventory`'s retire read the departure from its render's closure, so the
second handler restored the id the first had removed; one id was never
retired and `onSettled` never fired. jsdom hid it, because `fireEvent` flushes
between events. The regression test, *settles when two departures end in the
same batch* in `TileInventory.test.tsx`, ends both inside one `act`, and
failed before the fix.

This is the risk the plan's review named for T66 — removing Next Round turns
a missed `animationend` from a ghost tile into a frozen run — arriving through
a path none of the three listed cases covered.

# M6b walked: the stepped rack, measured where it binds

Branch `feat/M6b-classic-rack-motion`, stacked on M6a. Chromium via the
Playwright MCP server against `npm run dev`, and `npm run test:e2e`.

## The 320px gate, and an instrument 32px short of the app

The first sweep after T71 failed at 305 and 320: *Classic at twenty* put five
elements past the right edge. Two causes:

1. **The gallery stage was narrower than the app.** The gallery's own 16px
   inset left the arena 249px inside it at a 305px content box, against the
   app's 281px. The Classic tray at its narrow size needs 280px and may not
   shrink below the 44px target minimum. Endless had been surviving the same
   gap by 3px, because its rack overhangs its own box rather than the
   viewport. Below 40rem the stage now takes the page's full width, as the
   arena does (#130).
2. **The rack chose its size a frame late.** T71 first measured the rack with
   a `ResizeObserver`; the sweep, reading straight after the click, caught 7
   columns, and one frame later there were 6. Committing the change with
   `flushSync` inside the observer closed the frame but raised
   `ResizeObserver loop completed with undelivered notifications` on every
   size switch — the new height toggled the page scrollbar, which changed the
   width in the same frame. Observing a width-only sentinel did not help, for
   the same reason. **The size is now a CSS container query on the rack**:
   resolved in style, with no observer, no state and no loop. The component
   names the size (`data-size`) and draws the narrow fallback's whole rows (24
   cells at twenty); wide, CSS draws 21.

**Negative controls:** with the fallback query disabled, the 305px sweep and
the app-level 305px tests fail (four of four); with it, all pass. The e2e reads
once the tray is visible, which cannot tell the first frame from a later one;
the first frame is right because the size is resolved in style, not because
this reading proves it.

## Found in review, not in play

The re-seat wrote its frame inline and never removed it; inline beats a class,
so a re-seated tile discarded later would have computed `oz-reseat` instead of
its exit and frozen the round. No walk had yet reached a discard after round
11. The regression test (*lets a re-seated tile leave by its own exit later in
the run*) failed on `'oz-reseat'` before the fix; the full runs above then
discarded re-seated tiles freely.

## Found in bot review (PRs #155, #156)

Five bot findings were checked against the code; none was invalid.

- **A Classic win drew an equation nobody sees.** `handleNextRound` generated
  before the reducer saw the floor, against §1.8's order. Fixed on M6a with one
  `isAtClassicFloor` selector; the App test plays 28 rounds on an exact random
  sequence and threw "Random sequence exhausted" on the winning advance before
  the fix.
- **A discard inside the 300ms re-seat skipped its exit.** The inline
  `oz-reseat` outranked `oz-slide-off`, and the re-seat's end retired the tile.
  Not a freeze, since the retire still ran. Departing cells now drop the frame
  at once.
- **The rack at ten and below.** #156 amended §1.12 to "the Endless rack
  itself" while T71 and `decisions.md` still said a fixed `5 × 64×80`. The
  amendment stands, as Ori ruled: `5 × 64 + 4 × 8 = 352px` cannot fit the
  `281px` the 320px gate leaves. T71 and `decisions.md` now agree with it.
- **The e2e first-frame claim was stronger than its reading.** Narrowed; see
  the negative-controls paragraph above.
- **The tray jumps when the rail empties.** CodeRabbit read it as the drop
  landing off-target; it does not, because rail and seat are measured in one
  layout and the drop ends at `translate(0, 0)`. The rail does unmount as the
  drop starts, and the in-flow tray below it moves up by its height.
  **Gotcha, left as is:** Ori deferred the choice to the §7.6 review — keep
  the rail until the tile lands (the jump comes after the drop, and §1.12's
  "only while tiles are past capacity" needs a line), or keep §1.12 and the
  jump. Watch it on a phone before deciding; it lasts under a second.
  CodeRabbit's suggested patch fixes neither, since an empty rail is still
  56px against a populated one's tile height plus 9px. Marked at the rail's
  render in `TileInventory.tsx`.

Not fixed, noted: the rail is never the `56px` band §1.12 names. A populated
rail is the tile height plus its `8px` margin and `1px` rule, and grid rows
grow to fit the tile, so the CSS comment that a taller tile overhangs it does
not hold.
